# Device access: location and photo actions

Stage implementation, 30 October 2026. No terms-version activation or production configuration change.

- `useLocationAccess` is the sole caller of `getCurrentPosition`. No sidebar, background task or `watchPosition` reads location. General app startup does not request location; opening a location feature is the entry action.
- Opening Map (once its map instance is ready), legacy MapView or Near Me automatically offers the purpose explanation, with cancellation. Confirmation starts one location request and the platform dialog if required. A versioned device-local acknowledgement suppresses repeated explanations across reloads and feature visits; reopening a location feature then requests one position. Dismissing the explanation suppresses automatic offers on later visits; the locator button can reopen it. These local decisions are not platform permission grants; the platform still enforces access. Restricted storage falls back to session memory. No coordinates are persisted by the hook.
- Denial, timeout, unsupported devices and unavailable/invalid coordinates have DE/FR/IT/EN messages. The map/search remain available. A failed request does not move the search area. Coordinates are not read after leaving the feature; pending callbacks are ignored on unmount.
- Near Me sends coordinates and radius when a search is run. Existing map viewport persistence can store a map centre in browser storage. External tile providers receive requests for viewed areas. This is not a promise that request logs or all providers have no retention; the separate provider/retention checklist still applies.
- The feed’s camera button first explains camera and selected-photo access. Confirming either camera or the existing-image alternative remembers the versioned acknowledgement on this device; subsequent camera clicks open the capture picker directly, including after reload. Cancelling does not acknowledge the explanation. Confirmation synchronously activates the existing `input type=file capture=environment` inside the user’s click. The OS/browser controls the camera or picker and any required permission. Cancel does not activate it. An existing-image alternative uses the separate gallery input. No `getUserMedia`, microphone access, continuous stream or full-library API is introduced. Other image/document inputs continue to use the platform picker and user-selected files.
- Privacy & security contains device-access help and revocation instructions. Its “Show explanations again” button removes only the two versioned explanation decisions from browser storage and session memory, including dismissed location offers. The next map/camera action shows the corresponding explanation again. It does not change platform permissions, account data, tokens or unrelated preferences. It deliberately does not claim an app switch can revoke browser/OS permissions. Existing system grants may be remembered. This permission flow is separate from AGB acceptance.
- The unused legacy MapView follows the same entry action flow. Sidebar map previews use the saved/manual area, not a new location read.

## Verification

Browser regression coverage (390/1280 px, browser and simulated standalone PWA) spies on sensor calls: no general startup/sidebar reads even with a granted-permission mock; automatic explanation on feature entry; cancellation and later manual retry; confirmed single requests; remembered acknowledgements across reloads; denial/timeout/missing capability fallback; direct camera cancellation/confirmation and existing-file selection without publishing. Native camera hardware and the appearance of platform permission dialogs remain controlled by the actual device.

Reader privacy drafts DE/FR/IT/EN describe these flows. Previously accepted v1 remains byte/semantic-equivalent; no new acceptance or age gate is activated.
