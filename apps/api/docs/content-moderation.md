Stage feature code, disabled by default. No live moderation provider credential has been configured or called. Existing post/comment/profile/report behaviour remains unchanged while disabled. Production is excluded.

Enabled + missing key prevents startup. Other requests fail closed on provider failure; they never silently publish unchecked content. Keep the key server-side. No custom provider URL is accepted.

5. Open Admin → Content reports → Automatic content checks. Test an ordinary false positive, approve, then resubmit the unchanged content as the original user. Decisions never automatically publish anything.

## Behaviour and boundaries

- Posts (create/edit), comments/replies (create/edit), edited profile text and destination tips get text checks. New post photos, uploaded avatars, Trip covers and course submission images get image checks before public R2 upload. Every image in a multi-image submission is checked before any image is stored publicly. Trip documents/notes and financial data are not sent to moderation. Existing media and external OAuth avatar URLs are not retroactively scanned. This is not a claim that all historical or externally supplied content is safe.
- Model: `omni-moderation-latest`, fixed HTTPS endpoint; sends content/bytes only, no Fairwayd account identifier. Max 5 MB JPEG/PNG/WebP, checked signatures and MIME consistency. Provider timeout 15 seconds. Unsupported data or invalid responses fail closed. Legacy course image URLs and direct Trip cover URL changes cannot bypass enabled upload checks.
- Ordinary flagged inputs produce a review reference and are NOT published. Private quarantine bytes are held in the database, never a public bucket. At most five unexpired PENDING cases per user are created in a serializable transaction, plus a per-process 30-check/minute/user limiter. This is not a distributed global limiter; revisit before horizontal scaling.
- Approvals are bound to SHA-256 of the exact content and scope plus authenticated submitter, expire after 24 hours, and require the original user to resubmit. Changed content, other scopes and other users are not approved by that decision. Approved/rejected decisions atomically clear quarantine text/bytes. Child-safety flags have no retained payload and no ordinary admin override. Their retained content fingerprint prevents re-forwarding the same known-flagged payload under another user/scope; it is not a dedicated illegal-content hash-matching service.
- Pending/blocked records expire after seven days. A startup/hourly cleanup removes expired rows while enabled; list/preview/approval checks exclude expired rows even before cleanup. If disabled, cleanup resumes on next enable; do not claim a strict physical deletion deadline independent of service operation. Backups follow database retention. Account deletion cascades its cases. Review images require JWT + AdminGuard, no-store headers, nosniff, and deliberate click-to-view; bytes are not included in list responses or cached in browser storage. Object URLs are revoked after hiding/unmounting.
- Automated signals are fallible. They do not establish illegality, consent, copyright ownership, truth, or a complete child-safety finding. Reports, blocking, manual moderation, escalation and appeals remain necessary. Do not claim this feature alone guarantees App Store/Play approval or legal compliance.
- No raw content, images, API credentials or provider error bodies are logged. No automatic account suspension is performed on a classifier result. The appropriate legal child-safety response must be handled outside this normal false-positive workflow.

Sources: https://developers.openai.com/api/docs/guides/moderation and https://developers.openai.com/api/reference/resources/moderations/methods/create .
